# PR 编辑

## 流程

1. 强制问询：调用本 skill 后先问用户以下两问，未获答复不得继续
	- 「这个 PR 是否已在 Issue 中充分沟通？」
	- 「目标合并的仓库和分支是哪个？」
2. 收集改动：读分支相对目标分支的全部 commit 与改动文件（`git log origin/<目标分支>..HEAD --oneline`、`git diff origin/<目标分支>...HEAD --stat`）
3. 范围检查：一个 PR 只做一个独立功能，对应一个分支；多个功能须拆成多个 PR，禁止合并在一个 PR 里或混入无关改动；改动文件不超过 20 个，超限须在「改动」中说明原因
4. 定性：识别主要类型与范围，按规模定档：小型（1–3 个文件的简单修复）、中型（功能或重构）、大型（重大功能或架构变更，先建议拆分）
5. 写标题：约定式提交格式，一句话、60 字符内、不加句号；只有 1 个 commit 取其 subject，多个 commit 归纳一条主干；归纳不出一条主干说明含多个功能，退回第 3 步拆分
6. 按模板逐段写描述：小型 PR 可省略「动机」，有关联任务才补「关联问题」
7. 对照验收清单自检后提交

## 标题

```text
<type>(<scope>): <简明描述>
```

type 只用 feat、fix、docs、style、refactor、perf、test、chore、ci、revert；scope 为模块或领域，可省略。工单编号不进标题，放「关联问题」。  

- 正确：`feat(auth): 新增 OAuth2 登录并支持 Google SSO`
- 错误：`Update code`、`Fix bug`、`EXAM-1234`

## 模板

````markdown
### 摘要

2–3 句说清改了什么，从高层描述结果，不写实现细节。

### 动机

为什么改：要解决的问题、业务或工程目标。

### 改动

按领域或分层分组列出关键改动，改动文件超过 5 个必须分组，超过 20 个须说明原因；写明重要设计决策和不显然的实现选择。

- `path/from/repo-root.md`：一句话说明

**破坏性变更**

仅有时写，说明破坏了什么和迁移路径。

### 验证

写可复现的命令或步骤；没有自动化测试就写手工验证步骤。依赖与环境配置须完备，他人拉取分支后无需执行隐式命令即可直接运行；并注明未覆盖的边界与风险。UI 改动附改动前后截图，大段输出用 `<details>` 折叠。

### 关联问题

仅有任务或 Issue 时写，没有就不写这段，如 `Closes #123`。
````

## 文件引用

- 默认用相对仓库根目录的完整路径，放在行内代码里，如 `docs/bylaw/index.md`
- 需重点讨论的几行用固定 commit SHA 的永久链接；禁止链到 `main`，合并前新文件会 404，改过的文件显示旧代码
- 禁止用本地绝对路径或无上下文的裸文件名

## 验收清单

- [ ] 已问询用户 Issue 是否充分沟通、目标合并仓库与分支，并获答复
- [ ] 一个 PR 只含一个独立功能、对应一个分支，未合并多个功能或混入无关改动
- [ ] 改动文件不超过 20 个，超限已在「改动」中说明原因
- [ ] 标题与 commit 对得上，未超出 commit 范围
- [ ] 标题为约定式提交格式，一句话、60 字符内、无句号，不含工单编号
- [ ] 摘要 2–3 句，未写实现细节
- [ ] 动机写了为什么，而非重复做了什么（小型 PR 可省）
- [ ] 改动按领域分组，超过 5 个文件未平铺
- [ ] 破坏性变更已单独标出，未埋在正文中
- [ ] 模板内各段大标题为三级标题
- [ ] 验证写了可复现的命令或步骤，依赖与环境配置完备、拉取即可运行
- [ ] 文件引用为相对路径或 commit 永久链接，无 `main` 分支链接
- [ ] 关联问题仅在有关联任务或 Issue 时写入
- [ ] 未编造 commit 里没有的改动
- [ ] 标题、段落、列表、代码块之间各留 1 个空行
- [ ] 全文小于 150 行
